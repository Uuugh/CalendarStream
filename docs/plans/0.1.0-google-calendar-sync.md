# Plan: Google Calendar sync (0.1.0)

Status: **proposed** · Written 2026-10-20 · Target: first minor version, `0.1.0`

## Goal

Let CalendarStream write the schedule **directly into a Google calendar it owns**, through Google's
Calendar API, instead of relying only on Google subscribing to the `.ics` feed. This gives:

| | Today (subscribed feed) | With Google sync |
|---|---|---|
| Update delay in Google | 8–24 hours (Google re-checks feeds on its own schedule) | Seconds after CalendarStream sees a change |
| Per-event colours (tags) | Not possible: Google ignores colours in feeds | Yes: tags use Google's 11 event colours |
| Calendar colour | Each viewer picks it in Google | Set from CalendarStream (any colour, if Google allows it for this scope; see open question 1) |
| Calendar name | Only read when first added | Kept in step with CalendarStream (**F2** from the 0.0.10 list) |
| Edits, hides, added events | Yes | Yes (same rules as the feed) |

The `.ics` feed and the subscribe page stay as they are, for Apple Calendar and for other people.

## How it works

1. **Connect once.** In the **Settings** menu (☰), *Google Calendar → Connect* sends you to Google's
   sign-in, where you approve CalendarStream. Google returns a long-lived *refresh token*, which
   CalendarStream stores in the database, encrypted.
2. **Its own calendar.** CalendarStream creates a new calendar in that Google account, named like
   the feed (e.g. "United CCS Schedule"). It never touches your other calendars: it uses the narrow
   permission `calendar.app.created`, which only allows calendars CalendarStream created.
3. **Keep it in step.** Every time the published schedule changes (download, upload, edit, hide,
   added event, tag or name change), CalendarStream compares what Google should have with what it
   last sent, and creates, updates or deletes only the events that changed. A full check also runs
   at startup and once a day, to repair anything changed or deleted by hand in Google.
4. **Colours** (decided 2026-10-20).
   - **Tags use Google's event palette directly.** Each tag row offers Google's 11 named event
     colours (Tomato, Flamingo, Tangerine, Banana, Sage, Basil, Peacock, Blueberry, Lavender, Grape,
     Graphite) instead of a free colour picker, so what you pick is exactly what Google shows; the
     month view uses the same colours. Existing tags move to the nearest Google colour, once.
   - Events with no matching tag use the calendar's colour (the default colour), which keeps its
     free colour picker.
5. **Disconnect.** *Disconnect* revokes CalendarStream's access in Google and stops syncing.
   It asks whether to also delete the Google calendar it created.

## What gets written to Google

| CalendarStream | Google event |
|---|---|
| Title, location, notes | Summary, location, description (plus a last line: "Synced by CalendarStream") |
| Timed / all-day, start, end | `start`/`end` as `dateTime` + time zone, or `date` for all-day |
| CCS+ "free" items (days off, reserve) | Shown as *free* (transparency), like the feed |
| Hidden from Google | Not written (deleted if it was there) |
| Tag colour | `colorId` (the Google event colour chosen for the tag) |
| No matching tag | No `colorId`, so the event takes the calendar's colour |
| Event identity | A Google event ID derived from the CCS+ UID, so syncing is repeatable and can't create duplicates |

Reminders: see open question 3.

## Changes to CalendarStream

**New module `app/gsync.py`**
- OAuth 2.0 "web server" sign-in: build the Google consent URL (with a one-time `state` value to
  prevent cross-site use), handle the callback at `/google/callback`, and refresh access tokens.
- Calendar API calls over HTTPS with `httpx` (Google isn't behind Akamai, so a normal HTTP client
  is fine): create/patch the calendar, set its list colour, and insert/patch/delete events.
- The sync engine: desired events → diff against the `google_events` table → API calls, with
  retry and back-off on Google's rate limits, and a per-sync cap so a bad change can't flood the API.

**Database (created automatically)**
- `google_events`: CCS+/CalendarStream UID → Google event ID, content hash, last synced.
- `kv`: `google` (connection state: calendar ID, account e-mail if shown, last sync, last error),
  and the encrypted refresh token.

**Settings menu (☰)** (first use of the empty menu):
- *Google Calendar*: Connect / Disconnect, connected account, last sync and result, *Sync now*,
  and the reminder setting.

**Status page**
- The activity log records each Google sync ("Google: 3 updated, 1 deleted").
- The status line shows Google's state (connected / last sync / error).
- The tag editor shows the Google colour each tag maps to.

**Secrets and settings**
- `$MNT_DOCKER/.secrets/GOOGLE_CLIENT_ID.txt` and `GOOGLE_CLIENT_SECRET.txt`, mounted as Docker
  secrets like the others. Without them, the Google section explains how to set them up and the
  rest of the app is unchanged.
- The refresh token is encrypted with a key derived from `DB_PASSWORD`, so a copy of the database
  alone can't be used to reach your Google account.
- `PUBLIC_URL` must be the public **HTTPS** address, because Google sends you back to
  `PUBLIC_URL/google/callback` after sign-in.

## One-time Google setup (you)

About 10 minutes in the Google Cloud Console; the release will include step-by-step instructions
with screenshots in the README.

**You already have a Google OAuth credential.** It can be reused if, in its Google Cloud project:
the **Google Calendar API** is enabled; the client's type is **Web application**; its authorised
redirect URIs include `https://<your PUBLIC_URL>/google/callback`; and the consent screen is
**In production** with the `calendar.app.created` scope added. Otherwise, steps 2–4 below fix it.
Never paste the client secret into a chat; it only goes into the secret file.

1. Create a project (e.g. "CalendarStream") and enable the **Google Calendar API**.
2. **OAuth consent screen**: *External*, app name "CalendarStream", your e-mail as support and
   developer contact, and the scope `…/auth/calendar.app.created` (plus `openid email` if you want
   the connected account shown; see open question 4).
3. **Publish the app** ("In production"). In *Testing* mode Google expires the sign-in every
   7 days. A personal app that isn't verified by Google still works in production: Google shows an
   "unverified app" warning when you connect, which you can accept, and it's limited to 100 users.
4. **Credentials → OAuth client ID → Web application**, with the authorised redirect URI
   `https://<your PUBLIC_URL>/google/callback`.
5. Save the client ID and secret into the two secret files and restart the stack.

## Delivery

Built on a branch and released as `0.0.x` betas while it's developed, so `main`/`beta` keep working:

1. **Connect / disconnect**: settings menu, OAuth sign-in, encrypted token, creating the calendar.
2. **Event sync**: diff engine, create/update/delete, startup and daily full check, activity log.
3. **Colours and name**: the tag editor's Google palette (and moving existing tags to it), event
   colours in Google, calendar colour and name kept in step.
4. **Docs and hardening**: setup guide, error states (revoked access, quota, Google outage),
   reminder setting.

When you're happy with it, it becomes **0.1.0**, going through the agreed stable flow: programming,
commenting and security reviews (repeated until clean), then your test and approval.

**Testing**: this workspace can't reach Google, so automated tests run against a mock Google API
that behaves like the real one (sign-in, calendars, events, colours, rate limits, revoked tokens).
The real end-to-end test is yours, in step (d) of the stable flow.

## Risks and limits

- **Google's colour palette is fixed** for events (11 colours), so tags can only use those. That's
  by design: what you choose is what Google shows.
- **One Google account.** The sync writes to the account that connects. Others can still subscribe
  to the feed, or you can share the Google calendar from Google itself.
- **Avoid doubles.** If you keep the old subscribed calendar in Google too, events appear twice.
  The connect screen will remind you to remove the subscription.
- **Google can change its rules** (scopes, verification). The narrow scope keeps that risk low.

## Open questions for you

1. **Calendar colour in Google.** With the narrow permission, Google may not let CalendarStream set
   the calendar's colour in your calendar list. If not, should it (a) leave the colour to you in
   Google, or (b) also ask for the "manage your calendar list" permission (`calendar.calendarlist`)?
2. **Keep the feed?** Plan: yes, the `.ics` feed and subscribe page stay for Apple Calendar and
   other people. Remove them instead?
3. **Reminders** on synced events: none (recommended for days off and reserve), or your Google
   defaults?
4. **Show the connected Google account** (e.g. "Connected as you@gmail.com")? That adds the basic
   `openid email` permission.
5. **Which dates?** From the start of the current month onward (recommended), or everything in the
   CCS+ file including past months?
