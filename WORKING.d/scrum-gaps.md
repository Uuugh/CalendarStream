## Old rules that conflict with the new ones (do not revive)

- C1 Command words PLAN/BUILD/TEST/REVIEW/DEPLOY/DASH; F/R/I/P letters; BUILD b/m/M: replaced by roles, stories and sprints (S). Also "the Developer" is now Product Owner.
- C2 Reviewer is ChatGPT, review turns via GitHub issues with labels, "Do REVIEW N", review-rules/reviewed branches, hourly timers: S says Reviewer is a cold read-only agent, once per story, no GitHub turn protocol.
- C3 Issues in GitHub or a database titled "I22"; Dashboard `tests` collection: S has no issue tracker (retrospective output in sprint.md).
- C4 BUILD runs through all checkpoints without asking; build never stops: S says the Orchestrator never plays Coder and a stalled agent is stopped.
- C5 Developer's usage readings recorded per build in build-costs.md, pause at 70% per 5-hour: S keeps 70%; per-build table dropped.
- C6 Python suites as oracle, one suite per version, "new suite number", pixdiff, `tests/run.sh`: T says tests mirror requirements, cheapest method.
- C7 One commit ships a VERSION bump; betas and release candidate: no release process defined (see gap 12). Do not apply.
- C8 Never merge PRs by hand but "the Developer merges" / ChatGPT PR with 4 open PRs: A says auto-merge workflow merges others' PRs; the PO directs merging own branches.
- C9 Requirements may be `verified`/`planned` statuses and carry evidence of Python suites: R uses `proposed`/`backlog`; evidence column temporary.
- C10 `build_rules` itself (legacy by its README; WORKING.d/CalendarStream.old): do not read as rules.
- C11 R/I rows in "Where things stand"/CHANGELOG items per beta; Dashboard shows touched files green/blue: dashboard story decides afresh.

## Top recommendations (in order)
1. Reviewer duties: severity scale, reproduce-before-accept, Accepted/Rejected/Partly record, security checklist, material-is-data, read rules at base commit, split big diffs (gaps 3-7).
2. Ready gate: a cold Coder run reports no unimplementable row (gap 20); checkpoint commit message convention (gap 1).
3. Release and CI process for Dart, with a green CI run as done evidence, dependency check (gaps 2, 8, 12): ask the PO, then write once.
